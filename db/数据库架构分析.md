# Chatwoot 数据库架构分析

## 概述

Chatwoot 采用去外键设计的 PostgreSQL 数据库架构，通过字段命名约定和业务逻辑维护表间关系。这种设计在保持开发灵活性的同时，确保了数据的一致性和系统的可扩展性。

## 核心架构特点

- **多租户架构**: 以 `accounts` 为根节点实现租户隔离
- **多态关联**: 通过 `type/id` 字段组合实现灵活的表关联
- **JSON 存储**: 大量使用 JSONB 存储配置和元数据
- **AI 原生**: 集成 PostgreSQL vector 扩展支持 AI 功能
- **性能优化**: 使用 GIN 索引、pg_trgm 扩展等优化性能

## 表间依赖关系

### 1. 多租户架构（以 accounts 为根节点）

```
accounts (根实体)
├── 包含字段: id, name, domain, feature_flags, limits, settings
└── 关联: 几乎所有业务表都包含 account_id 字段
```

**核心关系**:
- `accounts` → `account_users` → `users` (用户关联)
- `accounts` → 所有业务数据表 (多租户隔离)

### 2. 用户和权限体系

```
accounts ←→ account_users ←→ users
    ├── custom_roles → custom_role_templates
    ├── custom_role_audit_logs (审计日志)
    └── agent_capacity_policies (坐席容量管理)
```

**关键表**:
- `users`: 用户基础信息
- `account_users`: 用户-账户关联，包含角色信息
- `custom_roles`: 自定义角色定义
- `custom_role_audit_logs`: 角色变更审计

### 3. 渠道管理体系（多态关联设计）

```
accounts → inboxes ←→ [channel_*] 表群
    ├── channel_web_widgets (网站插件)
    ├── channel_email (邮件渠道)
    ├── channel_facebook_pages (Facebook)
    ├── channel_whatsapp (WhatsApp)
    ├── channel_telegram (Telegram)
    ├── channel_sms (短信)
    ├── channel_voice (语音)
    └── channel_* (其他渠道)
```

**多态关联机制**:
- `inboxes.channel_id` + `channel_type` 实现多态关联
- 支持统一管理多种通讯渠道
- 每个渠道类型有独立的配置表

### 4. 客户关系管理

```
accounts → contacts ←→ contact_inboxes ←→ inboxes
    ├── additional_attributes (扩展属性)
    ├── custom_attributes (自定义属性)
    └── notes (客户备注)
```

**客户数据结构**:
- `contacts`: 客户基础信息
- `contact_inboxes`: 客户与渠道的关联关系
- `notes`: 客户相关备注记录

### 5. 对话和消息体系

```
conversations (核心业务实体)
├── account_id → accounts
├── inbox_id → inboxes  
├── contact_id → contacts
├── assignee_id → users (分配的坐席)
├── team_id → teams (分配的团队)
├── campaign_id → campaigns (营销活动)
├── sla_policy_id → sla_policies (SLA 策略)
└── messages
    ├── sender_id (多态: users/contacts)
    ├── attachments (附件)
    └── content_attributes (消息属性)
```

**消息处理链路**:
1. 客户通过渠道发送消息
2. 系统创建/更新对话记录
3. 消息存储在 `messages` 表
4. 附件单独存储在 `attachments` 表
5. 触发自动化规则和通知

### 6. 团队协作体系

```
accounts → teams ←→ team_members ←→ users
accounts → inboxes ←→ inbox_members ←→ users
    ├── assignment_policies (分配策略)
    ├── agent_capacity_policies (坐席容量策略)
    └── working_hours (工作时间)
```

**协作机制**:
- 团队管理：用户可以属于多个团队
- 渠道权限：控制用户访问特定渠道
- 自动分配：根据策略自动分配对话

### 7. 知识库体系（层级结构）

```
accounts → portals → categories → folders → articles
    ├── article_embeddings (AI 向量存储)
    ├── related_categories (分类关联)
    └── portals_members (门户成员)
```

**知识库结构**:
- **Portal**: 知识库门户，支持多门户
- **Category**: 文章分类，支持多级分类
- **Folder**: 文章文件夹组织
- **Article**: 具体文章内容
- **Embedding**: 文章向量化，支持 AI 搜索

### 8. AI 功能体系

```
accounts → captain_assistants (AI 助手)
    ├── captain_documents (知识文档)
    ├── captain_scenarios (场景配置)  
    ├── captain_assistant_responses (AI 响应)
    ├── captain_inboxes ←→ inboxes (助手渠道关联)
    └── copilot_threads → copilot_messages (对话线程)
```

**AI 功能特性**:
- 使用 PostgreSQL `vector` 扩展支持向量搜索
- AI 响应支持多态文档关联
- 支持场景化的 AI 助手配置
- 集成 Copilot 对话功能

### 9. 自动化和规则引擎

```
accounts → automation_rules (自动化规则)
accounts → assignment_policies ←→ inbox_assignment_policies ←→ inboxes
accounts → sla_policies → applied_slas → conversations → sla_events
accounts → campaigns → conversations (营销活动)
accounts → macros (快捷操作)
```

**自动化流程**:
- **Automation Rules**: 基于事件的自动化规则
- **Assignment Policies**: 对话分配策略
- **SLA Policies**: 服务水平协议管理
- **Campaigns**: 主动营销活动
- **Macros**: 批量操作模板

### 10. 标签和分类体系

```
accounts → labels (标签定义)
tags ←→ taggings ←→ [任意实体] (多态关联)
    └── 支持对话、客户等实体的标签管理
```

**标签机制**:
- **Labels**: 账户级别的标签定义
- **Tags**: 全局标签池
- **Taggings**: 多态关联表，支持给任意实体打标签

### 11. 通知和订阅体系

```
accounts → users → notifications
    ├── notification_subscriptions (订阅管理)
    ├── notification_settings (通知设置)
    └── mentions (提及通知)
```

**通知类型**:
- 系统通知：对话分配、状态变更等
- 用户提及：@mention 功能
- 订阅通知：自定义事件订阅

### 12. 系统监控和审计

```
audits (记录所有实体变更)
reporting_events (业务指标事件)
sla_events (SLA 事件跟踪)
leaves (员工请假管理)
webhooks (外部系统集成)
```

**监控机制**:
- **Audits**: 完整的变更审计日志
- **Reporting Events**: 业务指标和性能数据
- **SLA Events**: 服务水平协议跟踪
- **Webhooks**: 第三方系统集成

## 关键设计模式

### 1. 多态关联模式

```sql
-- 消息发送者（用户或客户）
messages.sender_type + sender_id

-- 标签关联（可以给任意实体打标签）
taggings.taggable_type + taggable_id

-- AI 文档关联
captain_assistant_responses.documentable_type + documentable_id

-- 访问令牌所有者
access_tokens.owner_type + owner_id
```

### 2. 软删除和状态管理

```sql
-- 使用状态字段管理实体生命周期
conversations.status (0:打开, 1:已解决, 2:待处理)
campaigns.campaign_status (0:暂停, 1:运行中, 2:已完成)
articles.status (0:草稿, 1:已发布, 2:已归档)
```

### 3. JSON 存储模式

```sql
-- 灵活的属性存储
accounts.limits JSONB DEFAULT '{}'
conversations.additional_attributes JSONB DEFAULT '{}'
contacts.custom_attributes JSONB DEFAULT '{}'
automation_rules.conditions JSONB DEFAULT '{}'
```

### 4. 显示ID模式

```sql
-- 用户友好的显示ID
conversations.display_id (自动生成的序列号)
campaigns.display_id (营销活动编号)

-- 使用 PostgreSQL 序列和触发器实现
CREATE SEQUENCE conv_dpid_seq_{account_id}
```

### 5. 全文搜索优化

```sql
-- 使用 pg_trgm 扩展支持模糊搜索
CREATE INDEX index_messages_on_content 
USING gin (content gin_trgm_ops);

-- 客户信息搜索优化
CREATE INDEX index_contacts_on_name_email_phone_number_identifier 
USING gin (name gin_trgm_ops, email gin_trgm_ops, 
           phone_number gin_trgm_ops, identifier gin_trgm_ops);
```

### 6. 向量搜索支持

```sql
-- AI 向量搜索
CREATE EXTENSION vector;

-- 文章向量化
article_embeddings.embedding VECTOR(1536)

-- AI 响应向量化  
captain_assistant_responses.embedding VECTOR(1536)

-- 向量索引优化
CREATE INDEX USING ivfflat (embedding);
```

## 业务流程依赖链

### 1. 客服对话流程

```
客户消息输入 → 渠道接收 → 对话创建/更新 → 坐席分配 → 消息处理 → 回复发送
     ↓              ↓           ↓          ↓         ↓         ↓
contact_inboxes → inboxes → conversations → users → messages → attachments
```

### 2. 知识库管理流程

```
创建门户 → 设置分类 → 创建文章 → 内容向量化 → AI 搜索
    ↓        ↓        ↓        ↓         ↓
 portals → categories → articles → article_embeddings → AI 检索
```

### 3. AI 辅助流程

```
配置助手 → 上传文档 → 向量化处理 → 对话集成 → 智能回复
    ↓        ↓         ↓         ↓        ↓
captain_assistants → captain_documents → embeddings → conversations → responses
```

### 4. 自动化处理流程

```
定义规则 → 事件触发 → 条件匹配 → 执行动作 → SLA 跟踪
    ↓        ↓        ↓        ↓       ↓
automation_rules → events → conditions → actions → sla_events
```

### 5. 营销活动流程

```
创建活动 → 定义受众 → 触发条件 → 发送消息 → 效果跟踪
    ↓        ↓        ↓        ↓       ↓
campaigns → audience → trigger_rules → messages → reporting_events
```

## 总结

Chatwoot 的去外键数据库设计是现代 SaaS 客服系统的典型架构模式：

**优势**:
- 🚀 **开发效率高**: 无外键约束，便于快速迭代
- 🔧 **灵活性强**: JSON 字段和多态关联适应业务变化
- 🏗️ **扩展性好**: 多租户架构支持大规模部署
- 🤖 **AI 友好**: 原生支持向量搜索和 AI 功能

**注意事项**:
- 需要应用层保证数据一致性
- 依赖命名约定和文档维护关系
- 需要完善的测试覆盖数据完整性

这种设计在保持系统灵活性的同时，通过良好的架构设计和约定确保了数据的一致性和系统的可维护性，是值得学习的现代化数据库架构实践。
